## Phase 28 — execute_query 在 LIMIT>200 时「超时」的根因与修复
用户反馈：`SELECT * FROM kf_chat_message LIMIT 100` 33ms 正常，`LIMIT 1000` 执行超时。
- 排查：前端 `invoke` 无超时（Tauri 默认也不超时），所以「超时」是**后端链路卡住**。
- 根因（`src/db/mysql.rs` `query()`）：流式读取行，当 `count >= PAGE_LIMIT(200)` 时直接 `break`，但此时 MySQL 结果流仍有剩余行未读（LIMIT 1000 还差 800 行）。紧接着 `pool.close().await` 要关闭一个**仍处于 streaming 脏状态**的连接，sqlx 必须先把未读结果集排空/重置 —— 慢库/高延迟网络上卡住 → 前端一直 pending → 表现为「超时」。LIMIT 100 因未超 200、流自然读到 EOF，连接干净，秒回。这是两者行为差异的唯一代码原因。
- 修复 1（`src/db/mysql.rs`）：读够 PAGE_LIMIT 行后**不再 break**，改为继续排空剩余流（丢弃超出行、不解码），保证连接回到干净状态再 `pool.close`。
- 修复 2（`src-tauri/src/commands.rs`）：`execute_query` 用 `tokio::time::timeout(30s)` 包裹，慢查询/卡网络也能在 30s 后以明确 `查询超时` 错误返回，前端不再永久挂起。常量 `QUERY_TIMEOUT_SECS=30`（tokio 已启用 `time` feature）。
- 验证：`cargo check --no-default-features` ✅（src-tauri）。
- 提交：`git commit d635573` "fix(db): resolve execute_query hang on LIMIT > PAGE_LIMIT"。
- 待用户验证：重新 `cargo run`（Rust 改动需重新编译）后测 `LIMIT 1000`，应秒回 200 行（带 truncated 标记）而非卡死。

## Phase 29 — 给 execute_query 加结果分页（用户要求"做分页吧"）
背景：LIMIT>200 之前被截断/卡死问题修复后，用户希望真正**翻页看全部行**，而非只截 200 行。
- 关键决策（架构权衡）：分页模式**覆盖用户的 LIMIT**——`query_paged` 会 strip 掉 SQL 末尾的 LIMIT 子句，再 append `LIMIT page_size OFFSET page*page_size`，并用 `SELECT COUNT(*) FROM (<sql>) AS _cq_sub` 算真实 total。即 `LIMIT 1000` 被分页接管（每页 200，total 显示真实总行数，可翻页看全部）。代价：用户显式小 LIMIT（如 `LIMIT 5`）也会被拉宽到 page_size；这是 DBeaver/Navicat「按页获取」的标准语义。page_size 被 clamp 到 PAGE_LIMIT(200) 保证单页内存有界（ADR-006 bounded results）。
- 实现：复用 `browse` 已有的分页范式，**新增** `mysql::query_paged`（不动老的 `mysql::query`，它仍被 tui/app.rs、llm/tools.rs 调用，零影响）。
  - `src/db/mysql.rs`：新增 `query_paged(cfg, sql, database, page, page_size)` + `strip_limit_offset()`（regex `LIMIT n[,m]|LIMIT n OFFSET m`，OnceLock 缓存；同时去无 LIMIT 时的尾部分号）。total 用 COUNT 子查询，失败则 `None`（UI 隐藏 pager 降级）。
  - `src-tauri/src/commands.rs` `execute_query` 增加 `page: u32, page_size: u32` 参数，Mysql 分支改调 `query_paged`，透传 `total/page/page_size`；Redis 分支不变（total=None）。
  - `frontend/src/api.ts` `executeQuery(connId,query,db,page?,pageSize?)`，默认 page=0/pageSize=200（新增顶部 `const PAGE_SIZE=200`）。
  - `frontend/src/App.tsx`：
    - `runStatFor`：table 且有 total>n 时显示 `第 X 页 / 共 N 行`。
    - `runQuery`：执行时把 tab.sql 更新为实际执行的 q（`setActiveTab ... sql: q`），并传 `page=0,pageSize=PAGE_SIZE`。
    - 新增 `runQueryAt(page)`：用当前 tab 保存的 sql 翻页重查（不吃未保存的编辑器编辑）。
    - `goPage`：有 browseCtx 走 browseTable，否则走 runQueryAt。

## Phase 34 — INSERT/UPDATE 复制支持任意查询结果（用户反馈）
用户反馈："为啥复制INSERT和UPDATE，只有在浏览表的时候才能复制"。
- 根因：`rowsToInsert(table,...)` 和 `rowsToUpdate(table,...,pks,...)` 依赖 `browseCtx.table` + `result.primaryKeys`；ad-hoc 查询时 `browseCtx=null`、`result.primaryKeys=[]`（后端 `execute_query` 未查 PK）→ 按钮被 disabled。
- 改动（纯前端 `App.tsx`）：
  - 新增 `extractTableFromSql(sql)`：正则解析 `FROM \`?(\w+)\`?` 提取表名（支持 `db.table`），JOIN/UNION/子查询返回 null。
  - `copyRowsAs`：table 优先 `browseCtx.table` → `extractTableFromSql(active.sql)` → 占位符 `<table>`；INSERT/UPDATE 始终可用。
  - `rowsToUpdate`：`pks=[]` 时 fallback 为「所有列同时出现在 SET 和 WHERE」→ 生成模板 SQL，用户改 SET 值即可。
  - 右键菜单：移除 `disabled={!browseCtx}` 和「仅浏览表」提示；无 PK 时显示「无主键·全列定位」徽标。

## Phase 36 — 非 SELECT 语句被错误分页（用户反馈）

  - `query_paged` 入口判断：非 SELECT 或多语句直接走 `query()`（无分页、无总数），前端自动隐藏分页条。
